# `protoc-gen-micropb` design

Date: 2026-11-19. Status: approved and implemented.

## Intent

A project that has `.proto` files must be able to use them with `micropb` without writing the C++ structs by hand. `protoc-gen-micropb` is a `protoc` plugin in Python. It reads a `.proto` file and writes one header of plain C++26 structs that `pb::encode` and `pb::decode` accept. This is stage 3 of `2026-11-18-micropb-design.md`.

## Goals

* One command gives a header that compiles: `protoc --micropb_out=gen app.proto` writes `gen/app.pb.hpp`.
* The output looks like a struct that a person writes: no macros, no helper classes, no generated functions.
* The `.proto` file stays as it is. The PC tools continue to use it without a change.
* The plugin is one short Python file.

## Non-goals

* `map`, proto2, editions, groups, extensions, services, well-known types.
* A CMake function that runs `protoc`. The README shows the command.
* A new string type with storage. A string stays a `std::string_view`.

## Anti-goals

* A header that silently loses a field or a size. The plugin stops with an error that names the field.
* A build of the library or of its tests that needs `protoc` or Python.

## Approaches for the sizes

A `.proto` file has no capacity for a repeated field. Three sources were possible:

1. **An options file** in the NanoPB format next to the `.proto` file. The `.proto` file does not change and NanoPB users keep their files. **Selected by the user.**
2. Custom options in the `.proto` file. Each PC tool must then import `micropb.proto`, and existing files must change.
3. One default capacity for all fields. It uses too much RAM and cannot make fixed arrays.

## Use

```sh
protoc --plugin=protoc-gen-micropb=tools/protoc-gen-micropb.py --micropb_out=gen -I proto proto/app.proto
```

* Output: `<name>.pb.hpp` for each `.proto` file on the command line, in the same sub-folder as the `.proto` file.
* Options file: `<name>.options` in the folder of the `.proto` file. The plugin looks for it relative to the current folder and relative to each folder of the parameter `--micropb_opt=options_dir=<folder>`. A missing file is not an error.
* Dependencies: Python 3, the `protobuf` Python package, `protoc`. The plugin uses `google.protobuf.compiler.plugin_pb2` from the package, so it has no generated code of its own.
* Windows: `tools/protoc-gen-micropb.bat` starts the Python file, because `protoc` cannot start a `.py` file there. (Not verified in this session.)

## Mapping

`tests/vectors/vectors.proto` and `tests/vectors/messages.hpp` are the model.

| `.proto` | C++ |
| --- | --- |
| `package a.b` | `namespace a::b` |
| `int32`, `int64`, `uint32`, `uint64`, `bool`, `float`, `double` | `std::int32_t`, `std::int64_t`, `std::uint32_t`, `std::uint64_t`, `bool`, `float`, `double` |
| `sint32` ... `sfixed64` | `pb::sint32` ... `pb::sfixed64` |
| `string` | `std::string_view` |
| `bytes` | `std::span<const std::uint8_t>` |
| `enum E { E_A = 0; }` | `enum class E : std::int32_t { A = 0 };` |
| message field | the struct as a plain member |
| `optional T` | `std::optional<T>` |
| `repeated T` | `pb::repeated<T, N>`, `N` from `max_count` |
| `oneof name { A a = 1; B b = 2; }` | `std::variant<std::monostate, A, B> name;` |
| `import "x.proto"` | `#include "x.pb.hpp"` |

Rules:

* **Names** of messages, fields and enums stay as they are in the `.proto` file. A field name that is a C++ keyword gets a `_` suffix.
* **Enum values** lose the prefix `<ENUM NAME>_` when each value of the enum has it. The enum name is compared in SCREAMING_CASE, so `RxMode` and `rx_mode` both remove `RX_MODE_`. Each value is written with its number.
* **Nested** messages and enums become top-level types with the name `Outer_Inner`, as NanoPB does. Thus the order of the definitions can always be correct.
* **Order:** the plugin writes enums first, then the structs sorted so that each struct comes after the structs that it contains. Among independent structs the order of the `.proto` file stays.
* **Field numbers:** the members are in the order of the `.proto` file. A member gets `[[= pb::tag{N}]]` only when its number is not the previous number + 1. A `oneof` gets `[[= pb::oneof_tags<...>{}]]` by the same rule.
* **Types of other packages** are written with the full name, `::a::b::name`.
* The header has a first line `// Generated by protoc-gen-micropb from <file>. Do not edit.`, `#pragma once`, and only the includes that it uses. It has no timestamp and no absolute path.

## Options file

One rule for each line: a name pattern, then `option:value` pairs. `#` and `//` start a comment. The pattern is compared with the full name of the field (`package.Message.field`) and with the name without the package. `*` and `?` are wildcards. When more than one line sets the same option for a field, the last line wins.

| Option | Applies to | Result |
| --- | --- | --- |
| `max_count:N` | repeated | `pb::repeated<T, N>` |
| `max_count:N fixed_count:true` | repeated | `std::array<T, N>` (encode only, a rule of the library) |
| `max_size:N` | bytes | `pb::repeated<std::uint8_t, N>` |
| `max_size:N fixed_length:true` | bytes | `std::array<std::uint8_t, N>` |
| `int_size:IS_8`, `IS_16`, `IS_32`, `IS_64` | `int32`, `int64`, `uint32`, `uint64` | `std::int8_t` ... `std::uint64_t` with the sign of the field |

An option that the plugin does not know, or that does not apply to the field (for example `max_size` on a string), is ignored with a warning on `stderr`. Thus an existing NanoPB file works, and a typing error is visible.

## Errors

The plugin reports these to `protoc`, which prints them and stops. No header is written.

* A file that is not `syntax = "proto3"`.
* A `map` field. (proto3 has no groups. An `extend` block in a proto3 file can only add custom options, so the plugin ignores it: see "Changes during the implementation".)
* A repeated field without `max_count`. The message shows the line to add to the options file.
* A message that contains itself, directly or through other messages.
* A `oneof` with two members of the same type (the library rule `variant_duplicate_alternative`).
* A bad line in the options file, with the file name and the line number.

The compile-time checks of the library find all other problems when the header is compiled.

## Tests

* `tests/generator/test_plugin.py` (Python `unittest`): runs `protoc` with the plugin on small `.proto` texts and compares the header text or the error text. It covers each mapping rule, each option and each error.
* `tests/vectors/vectors.options` and the checked-in output `tests/vectors/vectors.pb.hpp`: a Python test makes the header again and compares it with the checked-in file.
* `tests/test_generated.cpp`: includes `vectors.pb.hpp`, encodes and decodes the generated types and compares the bytes with the `protoc` reference vectors. It needs no `protoc`, because the header is checked in.
* CMake adds the Python tests to CTest only when it finds Python, the `protobuf` package and `protoc`. Without them the other tests still run.

## Calls of the builder

* The output file name is `<name>.pb.hpp`. It does not collide with `<name>.pb.h` of the Google or NanoPB generators.
* Names are not converted to snake_case.
* A message field without `optional` is a plain member, as in `messages.hpp`. The encoder always writes it. Google's runtime omits it when it is unset.
* Nested types are flattened to `Outer_Inner`.
* A `oneof` loses the names of its members, because a `std::variant` has only types.

## Changes during the implementation

* An `extend` block is ignored and is not an error. In proto3 it can only define custom options, so no message field is lost. A file that defines its own options thus still works.
* An import gives an `#include` only when the file uses a type of the imported file. Thus `import "nanopb.proto"` does not ask for a header that does not exist.
* A member whose name is equal to the name of a type in the same struct makes the plugin write the full type name (`::pkg::inner inner;`). C++ does not accept the short form.
* New errors: two types with the same flattened name (`A_B` and `A.B`), `int_size:IS_8` on a repeated unsigned field (the library reads a sequence of `std::uint8_t` as `bytes`), `fixed_length` without `max_size`, an unknown plugin parameter.
* New warning: a pattern that matches no field. A wildcard rule gives no warning for the fields that it does not apply to.
* `max_size` applies only to a `bytes` field that is not repeated.
* A second test schema, `tests/generator/features.proto` with `shared.proto`, covers the rules that `vectors.proto` does not use. Its generated headers are also checked in and compiled.

## Changes after the review and for field lists

* The header now has a field list (`pb::fields_of`) for each message and no annotations: see `2026-11-19-field-lists-design.md`. The rule "a member gets `[[= pb::tag{N}]]` only where the numbers have a gap" no longer applies.
* `pb`, `std` and eight common macro names (`NULL`, `EOF`, `errno`, `stdin`, `stdout`, `stderr`, `assert`, `offsetof`) get the suffix `_`, as keywords do. The parts of a package name get it also.
* The options file is read as UTF-8 with or without a byte order mark. A file in a different encoding is a clean error.
* Warnings are printed also when an error stops the plugin.
* `max_count` and `max_size` accept 1 to 999999999.
* Enum values keep their names when the text after the prefix does not start with a letter.
* The plugin has no syntax that needs Python 3.12.
* Not changed, by decision of the builder: no message when no options file is found; a `(nanopb)` option in the `.proto` file is not read; an import of a proto2 file or of a well-known type gives an `#include` of a header that the user must generate; a type name collision between two files is not found; `[packed = false]` is ignored.
